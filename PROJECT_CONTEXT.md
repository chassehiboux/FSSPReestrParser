## Единый запуск — реализация v0.3.0

Главная кнопка объединяет выгрузку и реестры. Исходный XLSX выбирается первым через современный IFileOpenDialog с принудительным SetFolder в `RegistrySourceRoot`, затем календарь месяца/года без папки выгрузок. Прежние кнопки спрятаны в раскрываемом разделе «Отдельные операции». В авторизации подсказка: логин и пароль Windows, без `vostok\` в логине.

`internal/pipeline` хранит незавершённые запуски в локальной папке программы `pipelines/run-*/`: исходник-снимок, атомарный state.json, выгрузки, файловая блокировка Windows. Параметры/хэш исходника определяют возможность продолжения; завершённые запуски не переиспользуются. Отдельные неудачные запросы повторяются до 3 раз. Запись на целевой диск повторяется отдельно из локальной копии; до сверки проверяется полный ожидаемый комплект и хэши. При сбое — кнопка «Продолжить»; повторный выбор того же исходника и параметров также продолжает запуск. После успеха собственные локальные XLSX удаляются, журнал завершения остаётся.

Результат: новая «Сверка» рядом с исходником, внутри реестры и «Исх.» без даты; Windows убирает конечную точку, в Проводнике имя «Исх». В папке выгрузок только XLSX. При длинном локальном или сетевом пути имена сокращаются до `0001.xlsx` и далее, условия остаются в единой таблице. Реестры читают проверенные локальные снимки, соответствующие записанным файлам. Исходные выгрузки не удаляются при ошибке формирования реестров. Отдельные операции сохраняют прежние пути и поведение.

Реальный повтор на 12 имеющихся книгах с двумя искусственными сбоями записи: 3376 строк, 940 ДР по ИД, 22 по делу, 120569 строк выгрузки; все 6 реестров совпали по значениям с отдельной сверкой. Каталог проверки `local/pipeline-real/Сверка`. По просьбе заказчика дополнительный живой прогон не выполнялся, v0.3.0 уже опубликован. Локальный готовый EXE: `bin/release-0.3.0/FSSPReestrParser-windows-amd64.exe`.

## Что согласовали с заказчиком

- Windows 10/11 x64, у пользователей уже есть Chrome либо Edge, доступ к GitHub и корпоративной сетевой папке. Всего примерно 10–20 пользователей, обычно одновременно работает один.
- Приложение запускается по необходимости. Лёгкая поставка одним EXE, без Python и отдельного Chromium у пользователя. Выбран Go + Rod + Walk, используется установленный браузер.
- Каждый входит в Пирамиду своим логином и паролем. Неверный пароль должен приводить к понятному повторному диалогу, сетевые ошибки нельзя выдавать за неверный пароль. Сохранение пароля добровольное, защита Windows DPAPI.
- Админка видна и доступна только учётной записи Windows заказчика dzuikevich, проверка по SID. Отдельно проверяется обработчик открытия. Это ограничение интерфейса, а не защита сетевого JSON от ручного редактирования.
- Все настройки общие через корпоративную SMB-папку. Заказчик явно отказался от подписи настроек и не может настраивать права общей папки. Не вводить подписи/ACL повторно без нового запроса.
- Настройки должны расширяться на другие базы, департаменты и региональные профили: например, Курганская база для Кургана, другая база для Тюмени. Пока настроен только Курган.
- Headless включён по умолчанию; переключатель только у администратора для тестов. Заказчик сам временно выключал headless в рабочих настройках: не сбрасывать его выбор автоматически.

### Сохранение и повторный запуск

Файлы непосредственно в системной папке Downloads:

```text
Выгрузка ОВЗИД для реестров ФССП\
  yyyy.mm.dd\
    Курган - Направлены на исполнение (нет возбуждения).xlsx
    Курган - В исполнении (возбуждены ИП).xlsx
    ...
```

Одна папка на день, без номера N, без дополнительных подпапок и служебного JSON. Для связанных условий значения перечисляются в имени через дефис. После очистки имён коллизии получают стабильный суффикс по ключу задания, чтобы не перезаписать другой отбор.

При повторном запуске диалог показывает найдено N из N, недостающие/повреждённые файлы и кнопки «Перевыгрузить все», «Довыгрузить недостающие», «Отмена». Проверяются ожидаемое имя, структура XLSX и целостность ZIP. Готовый файл заменяется только после проверки нового; ошибка сохраняет предыдущий. Посторонние файлы не удаляются. Подтверждённый пустой результат полной перевыгрузки удаляет устаревший файл данного отбора. «Нет данных» не создаёт файл, поэтому при следующей довыгрузке проверяется снова. Старые тестовые папки с N сохранены.

Без служебного реестра сопоставление доверяет именам созданных приложением файлов: произвольно подложенная корректная книга с ожидаемым именем не проверяется на бизнес-содержимое.

## Кэш и общие настройки

Обычный `settings.json` в согласованной корпоративной папке FSSPReestrParser. Полный реальный UNC-путь и SID доступны локально в игнорируемом `local/bootstrap.json`, а для CI — в GitHub Secrets `FSSP_SHARED_PATH` и `FSSP_ADMIN_SID`. Не выводить их целиком в публичные документы и не коммитить рабочие конфиги. Ориентир размещения — корпоративная папка заказчика в разделе Excel/ВЗИД/FSSPReestrParser.

Публикация настроек атомарная, с проверкой версии от потери параллельных сохранений. На весь запуск фиксируется снимок настроек. При недоступности общего файла используется последняя корректная локальная копия с предупреждением. Если нет ни общего файла, ни корректной копии, требуется восстановление настроек, а не молчаливое создание пустого профиля.

Кэш полей и значений общий, отдельный для каждой пары база/департамент: `catalogs/<base_id>/<department_id>.json` рядом с общими настройками. Есть схема и UTC-время чтения живой формы, локальная копия. Во время выгрузки прочитанные живые поля асинхронно публикуются в общий кэш. В админке отсутствие, недоступность либо возраст более 7 суток отмечается как устаревший кэш; ровно 7 суток ещё допустимы. Кнопка «Обновить» обходит все настроенные базы и департаменты. Частичные успехи сохраняются, ошибки перечисляются. Сейчас реально прочитано по 57 полей для каждого из трёх департаментов.

Локальные данные приложения: `%LOCALAPPDATA%\FSSPReestrParser` — кэш, каталоги, защищённые учётные данные и сессии. Выгрузки остаются в Downloads. Не публиковать пароли, cookies, browser storage, выгрузки.

### Что важно не сломать при работе с Пирамидой

- В форме имя поля каталога `CaseStatusName`, фактический фильтр `CaseStatus_StatusName`. Числовые ID четырёх статусов при обследовании: 33, 100057, 100066, 100127. Значения разрешаются через живую форму департамента; старый кэш PyramidReports имел другой формат и не подходит как константа запроса.
