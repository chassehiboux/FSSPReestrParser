## Предлагаемая обработка сомнительных строк

Точное сопоставление и аналитика выполняются отдельно. Неточный кандидат не становится точным совпадением после очистки текста.

1. Сначала искать кандидатов по трём совпавшим ключам. Отмечать конкретное несовпавшее поле и показывать обе версии значения.
2. Для нескольких расхождений сужать поиск по сочетаниям полей и вариантам имени/номера, затем сравнивать кандидатов. Совпавший регистрационный номер ИП из исходника можно использовать как дополнительное подтверждение при аналитике; он не заменяет четыре основных ключа.
3. В ФИО отдельно сравнивать пробелы, неразрывные пробелы, ё/е и варианты фамилии в скобках. Не отбрасывать оглы, кызы, части двойных фамилий и не требовать ровно три слова. Скобки анализировать как варианты конкретной части имени, а не удалять их содержимое безусловно.
4. Небольшие опечатки оценивать по отдельным частям имени с опорой на другие поля. Новая фамилия при совпавших имени и отчестве — кандидат для проверки. Один общий процент сходства всей строки не считать доказательством.
5. Для номера ИД учитывать оформление и структурные части только при поиске кандидата. Не выбрасывать год, номер суда и суффикс без отражения этого расхождения в аналитике.
6. Для взыскателей применять явный согласованный словарь известных вариантов и отдельно объяснять отличие оформления. Не объявлять разные юридические лица одинаковыми только по похожему названию.
7. Для суммы показывать исходную сумму, сумму кандидата и разницу. Предварительная категория «расхождение до 0,10 руб.» обоснована выборкой. Любой допуск относится к аналитике и не меняет точный ключ.
8. При нескольких равноценных кандидатах не выбирать первую строку по порядку файла. Если надёжных подтверждений недостаточно, писать «Надёжный кандидат не найден».

Для аналитики предлагаются:

- «д.р.» — только подтверждённая дата при точном совпадении;
- «Результат сопоставления» — «Полностью совпало», «Не совпал взыскатель», «Не совпал номер ИД», «Частично не совпало ФИО», «Не совпало ФИО», «Не совпала сумма», сочетание причин, «Несколько кандидатов» или «Надёжный кандидат не найден»;
- «Основание подбора» — какие ключи совпали, характер расхождения и необходимость ручной проверки;
- отдельные поля кандидата: ФИО, номер ИД, сумма, взыскатель, «Предполагаемая д.р.», разница суммы, количество кандидатов;
- файл, лист и строка выгрузки для проверки человеком. При неоднозначности — отдельный лист «Кандидаты» в том же файле, связанный с номером исходной строки. Пятого файла не требуется.

Конкретную причину расхождения записывать относительно найденного кандидата, не выдавая гипотезу за установленный факт. У строки с единственным совпавшим ФИО недостаточно оснований утверждать, что остальные три значения ошибочны.

## Шаблоны и особые ситуации

Шаблон возбуждения содержит 11 столбцов, включая «Д.р. должника» на шестой позиции.
Шаблон окончания содержит 14 столбцов, совпадающих с исходным файлом, и не содержит ДР.
Предлагается добавить «Д.р. должника» после «Должник» в реестр окончания с ДР, а вариант без ДР оставить в исходном формате из 14 столбцов. Это требует согласования.
Одна и та же подтверждённая строка включается в оба реестра с ДР, без дополнительного отбора по статье/дате завершения, как указано в запросе.

Точное совпадение без ДР или с различными непустыми ДР предлагается направлять в вариант без ДР с отдельным объяснением в аналитике.
Повторы выгрузки с одной ДР не размножают исходную строку. При повторе с пустой и одной корректной непустой ДР предлагается использовать непустую с отметкой в аналитике. Невалидную дату не подменять пустым нулём или датой по умолчанию.
При отсутствии строк в одной из категорий предлагается всё равно создавать книгу с заголовками, чтобы каждый успешный запуск давал четыре файла.

Обрабатываются XLSX непосредственно выбранной папки, без автоматического обхода вложенных папок. Файлы блокировки «~$» пропускаются.
Повреждённая книга или отсутствие обязательного поля — понятная ошибка до публикации результатов, а не молчаливое исключение части базы.
Если обязательный заголовок неоднозначно повторяется, требуется явное правило выбора; нельзя молча брать первую колонку.
В обследованной выгрузке повторяется необязательный «Номер ИП». Дополнительный анализ ИП должен учитывать это, прежде чем использовать его как подтверждение.
Если в будущем входные ключи содержат формулы, потребуется проверка сохранённых вычисленных значений: приложение не должно подставлять пустое значение вместо отсутствующего результата формулы.

У Windows есть традиционный MAX_PATH 260, однако Microsoft отдельно указывает ограничение Excel в 218 символов при открытии файлов. Поэтому только проверки Windows недостаточно.
Предлагается постоянное имя подпапки «Сверка», сохранив запрошенные имена книг. Для указанного примера все четыре пути укладываются в 218, но запас у самого длинного — всего один символ.
Перед запуском необходимо проверить фактические длины всех четырёх путей. Для более длинного исходного расположения предложить выбрать более короткую папку сохранения либо перенести исходник, не выдавая обещаний, что longPathAware решит ограничения Excel.
Нельзя молча менять место сохранения или сокращать имена до непонятных обозначений.

Источники: [ограничения имени и пути в Excel](https://support.microsoft.com/en-us/support/known-issues/excel-doesn-t-fully-support-some-special-characters-in-the-filename-or-folder-path), [ограничения путей Win32](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation).

## Сохранение и повторный запуск — предложение

Пользователь видит отдельную панель процесса снизу: проверка входных файлов, чтение выгрузок с реальным счётчиком, сопоставление строк, формирование четырёх книг, сохранение. Есть отмена, итоговые количества и открытие папки результата, уведомление Windows.
На первом этапе предлагается не разрешать создание реестров одновременно с продолжающейся выгрузкой: база должна быть полностью сохранена и не меняться во время чтения.
Операция не требует входа в Пирамиду и не должна зависеть от доступности браузера или общих настроек.

Результаты сначала готовятся и проверяются во временном месте, затем заменяют комплект после подтверждения пользователя. Ошибка и отмена не должны повреждать прежние результаты.
Успех показывается только после сохранения всех четырёх книг. При ошибке во время замены нескольких файлов требуется восстановление прежнего комплекта или явное описание неполного восстановления; четыре отдельных переименования не являются общей атомарной операцией на SMB.
При одинаковом месяце результаты разных исходников в одной папке будут иметь одинаковые имена. Предлагается предупреждение с полным списком заменяемых файлов, без автоматической перезаписи. Нужный способ хранения нескольких комплектов требует уточнения.

## Технические выводы для будущей реализации

Выгрузки надо читать один раз и строить общий индекс четырёх ключей. Сканировать все файлы заново для каждой исходной строки не требуется.
Чтение потоковое, без загрузки всех 79 столбцов в полные объекты книги. Для точного прохода достаточно ключей, ДР и ссылок на источник, для аналитики — дополнительных индексов.
Проверочный локальный проход всех выгрузок и точного сопоставления занял около 53 секунд. Это время исследовательского Python-скрипта на локальных файлах, а не обещание скорости будущей Go-версии или SMB.
Исследовательские данные сохранены только локально. Для корректности начальной версии межзапусковой кэш выгрузки не нужен: он может скрыть обновление файлов.

Числовые ячейки Excel сравнивать как числовые значения без допуска, текстовые значения суммы не превращать автоматически в числа. Пробелы и формат отображения ячейки не являются частью числа.
В 115 из 940 совпадений XML исходника записывает сумму длиннее обычного денежного представления, но после штатного чтения Excel-числа обе записи имеют одинаковое значение binary64.
Независимое чтение исходного XML с числовым сравнением подтвердило 940 совпадений. Буквальное сравнение XML-строк сумм ошибочно дало бы 825.
Это не основание округлять все суммы до копеек или добавлять допуск в строгий ключ. Денежную разницу для аналитики вычислять отдельно без артефактов двоичной арифметики.

Сейчас в Go-проекте нет библиотеки работы с Excel. После согласования понадобится одна библиотека чтения/записи XLSX с поддержкой потокового чтения и сохранения оформления шаблонов. Новую зависимость выбирать и фиксировать отдельно после проверки возможностей, без runtime Python у пользователя.
Шаблоны предлагается встроить в EXE после разрешения добавления обезличенных шаблонов в репозиторий. Исходный файл и выгрузки в EXE/Git не включать.
